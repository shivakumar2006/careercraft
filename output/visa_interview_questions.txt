## 🔧 TECHNICAL QUESTIONS (Go & Backend Stack)
*Questions 1–5*

---

**Q1: Walk me through how Go handles concurrency. Can you explain goroutines and channels with a practical example?**

Hint: Reference your Go repos like `API-GO` and explain goroutines as lightweight threads managed by the Go runtime. Describe channels as typed conduits for communication between goroutines. Give a concrete example — e.g., spawning goroutines to process payment requests concurrently while using a channel to collect results safely.

---

**Q2: In Go, what is the difference between a pointer receiver and a value receiver on a method? When would you choose one over the other?**

Hint: Explain that pointer receivers modify the original struct while value receivers work on a copy. Mention that pointer receivers are preferred when the struct is large (avoiding copy overhead) or when mutation is needed. Tie this back to building reliable backend services where data consistency matters — relevant to Visa's financial data handling.

---

**Q3: How would you implement error handling in a Go backend service? What patterns do you follow?**

Hint: Go lacks exceptions, so discuss explicit error returns using the `error` interface. Mention wrapping errors with `fmt.Errorf` and `%w` for context, and using `errors.Is` / `errors.As` for checking error types. Highlight how proper error propagation is critical in payment systems where silent failures can cause financial discrepancies.

---

**Q4: Your `API-GO` repository suggests REST API experience. How would you design a versioned REST API endpoint, and why does versioning matter?**

Hint: Discuss URL versioning (`/v1/payments`) vs. header-based versioning, noting trade-offs in readability vs. cleanliness. Explain that versioning allows backward compatibility — critical at Visa where millions of clients depend on stable endpoints. Mention using OpenAPI/Swagger documentation to communicate contract changes to consumers.

---

**Q5: What is the difference between unit tests and integration tests? How have you implemented unit tests in Go?**

Hint: Unit tests validate isolated logic using Go's built-in `testing` package and mock dependencies with interfaces. Integration tests validate component interactions — e.g., a service talking to a real database. Reference your Go repos and mention using `table-driven tests` in Go, which is idiomatic and demonstrates maturity. Connect this to the JD's explicit requirement for unit and integration test contributions.

## 🏗️ SYSTEM DESIGN QUESTIONS
*Questions 6–9*

---

**Q6: Design a payment transaction API that handles high throughput and ensures no duplicate transactions are processed.**

Hint: Introduce idempotency keys — a UUID sent by the client that the server stores and checks before processing. Discuss a layered architecture: API Gateway → Service Layer → Database with a unique constraint on the idempotency key. Mention distributed locking or database transactions for race conditions. This directly mirrors Visa's core infrastructure challenge at scale.

---

**Q7: How would you design a system to ensure a backend service remains reliable during partial infrastructure failures?**

Hint: Cover circuit breakers to prevent cascading failures, retry logic with exponential backoff, and health check endpoints. Mention graceful degradation — e.g., returning cached data if the database is briefly unavailable. Tie in monitoring and alerting (Prometheus/Grafana) for production observability, which aligns with the JD's mention of production support responsibilities.

---

**Q8: A microservice processes thousands of financial events per second. How would you structure its database interactions to avoid becoming a bottleneck?**

Hint: This targets your identified gap in databases. Discuss connection pooling, read replicas for query offloading, and indexing strategies for frequent query patterns. Mention async writes via a message queue (Kafka) for non-critical paths while keeping synchronous writes for critical financial records. This shows awareness of Visa's scale requirements.

---

**Q9: How would you approach moving a new feature from design to production safely? What stages would you include?**

Hint: Walk through feature flags for gradual rollout, branch-based development, PR/code review, automated CI/CD pipelines, staging environment testing, and canary deployments. Mention rollback strategies. This maps directly to the JD's goal of helping you "learn how features move from idea to production" — showing you already understand the full lifecycle.
